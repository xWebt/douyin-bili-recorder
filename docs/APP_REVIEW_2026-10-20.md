## 结论摘要

三个现象都不是“偶发”，分别对应明确的系统性缺陷：

1. **新主播不录**：缓存空间准入策略把新分段卡死（实机 19.6 GB 已用 + 18.14 GB 预留 > 30 GB 上限），默认又是“手动检查一次”，再叠加空间不足被显示成“未开播”。目标配置本身在下一轮轮询会热更新（详见 P1 修正）。
2. **云盘慢/失败**：链路仍是 OpenList 单连接 `PUT /api/fs/put`；OpenList token 过期后不会自动刷新；所谓“夸克快速通道”在当前架构里不存在。
3. **弹幕视频糊**：烧录是二次编码，优先走 `h264_videotoolbox`，回退 `libx264 veryfast`，均为固定码率；原画最高只给 24 Mbps，4K/高码率源会被压低，且没有使用源码率。

## P0：直接导致当前故障

### P0-1 缓存空间策略会把新主播“永远卡住”

**代码**

- `src/douyin_bili_recorder/encoding.py:55-58`：带弹幕烧录时，按“原始 FLV + 烧录 MP4”两份文件预留：`(8.4 + 8.4) × 1.08 = 18.14 GB/小时`。
- `src/douyin_bili_recorder/pipeline.py:929-990`：只有 `usage + peak <= max_cache_gb` 才允许开始下一段，否则等待；没有“清理失败分段/降低分段时长/仅预留渲染文件”的降级路径。

**实机证据**

- 日志 13:39:41–13:40:52 连续输出：
  `waiting for uploads to free space for 7JIA九芊岁: used 19.67 GB, need 18.14 GB`
- `max_cache_gb = 30`，19.67 + 18.14 = **37.81 GB > 30 GB**，所以新主播永远无法开始下一段。
- 这 19.6 GB 来自一场上传失败后保留的本地文件：P01 MP4 8.6 GB + P01 FLV 6.6 GB + P02 FLV 4.4 GB；上传失败后系统按规则保留文件，但没有自动清理/重试闭环。
- 更严重的是：**默认缓存 10 GB 小于 18.14 GB 的单段预留**。只要开启“录制并烧录”+原画，默认配置下从 0 开始也永远无法录制。

**影响**

- 新加主播表现为“等待空间”或（见 P0-6）被错误显示成“未开播”，实际是预算死锁。
- 现有主播也会在下一分段前被卡住。

### P1 修正：目标配置主循环可以热更新，但等待阶段不响应暂停/删除

**更正**：我最初用绕过 `_target_loop` 的脚本得到“worker 配置永远不更新”的结论，那个复现是错的。用真实 `_target_loop` 复测后，watch_mode/enabled 会在下一轮 `_reload_runtime_settings()` 中更新，暂停请求也会生效。

**仍然存在的真实问题**

- `pipeline.py:929-990` 的 `_wait_for_capacity()` 和 `pipeline.py:1770+` 的 `_wait_for_reconnect()` 只检查 shutdown/interrupt，不检查 `_paused_targets` / `_removed_targets`。在这些等待阶段点暂停或删除主播，最多要等到容量释放/重连宽限期结束才退出。
- `recorder.py` 的子进程在暂停/删除时没有被立即 terminate（见 P0-5 修正）。
- 保存提示“下一分段或重启后生效”对主播配置是误导：实际下一轮轮询就生效，不需要重启。

**影响**：不是“所有配置都不生效”，而是“暂停/删除在特定等待阶段不够及时”，需要在等待循环里加入暂停/删除检查并终止录制子进程。

### P0-3 新主播默认“手动”且手动请求只消费一次

**代码**

- `web/app.js:1161`、`web/app.js:1692`：新增主播固定 `watch_mode: "manual"`。
- `pipeline.py:500-506`：manual 模式下只有存在 manual request 时才检查一次；检查完请求文件即被删除（`_consume_manual_request`）。
- 如果点击“单独开始”时主播离线，这一次检查会返回“未开播”，**之后不会自动再检查**；用户必须再次点击。

**影响**

- 用户添加主播后以为在监控，实际只在点击瞬间检查一次。
- 新增主播恰好离线时，表现为“永远不录”。

### P0-4 添加主播时没有强制解析成“可长期监控的直播间地址”

**代码**

- `web/app.js:1685-1699`：普通“添加”直接保存输入框原文（可能是抖音分享文案、短链、主页链接）。
- `douyin.py:127-128`：解析失败时 `canonical_url = final_url`，会把主页/短链原样返回，而不是报错要求提供直播间地址。
- `recorder.py:45`、`recorder.py:127`：录制时把 `target.url` 原样交给 biliup；分享文案会直接导致失败。
- `extract_shared_url()` 只在解析接口内部使用，保存/录制链路没有再次规范化。

**违反需求**

- `docs/CURRENT_REQUIREMENTS.md`：必须从分享文本解析出可长期监控的直播间地址，而不是保存主页或短链。

**影响**

- 用“添加”而不是“解析并添加”时，目标 URL 可能是整段中文分享文案 → `_probe_live_with_recorder` 永远失败 → 状态显示“未开播”。
- 解析失败时静默保存主页 → biliup 无法录制，用户无感知。

### P1 修正：暂停/删除在主循环生效，但不会立即终止当前录制子进程

**更正**：真实 `_target_loop` 复测中，暂停请求会在 2 秒内让 worker 停止调用 `record_and_upload`，恢复也能正常继续；主循环的热更新/暂停不是坏的。

**仍然存在的真实问题**

- `pipeline.py:557-643`：内层循环因暂停/删除 break 后，没有调用 `process.terminate()`；biliup 下载进程可能继续写文件，直到自然结束或应用退出。
- `pipeline.py:1770+`：`_wait_for_reconnect()` 不检查暂停/删除，可能在暂停后继续等待重连并恢复录制。
- `pipeline.py:929-990`：`_wait_for_capacity()` 不检查暂停/删除，暂停后仍可能在等待空间里停留。

**影响**：暂停/删除的主要状态逻辑可用，但“当前录制子进程”和“等待阶段”没有立即停止，仍会写文件或延迟退出。修复应围绕子进程注册与等待循环检查，而不是重写暂停状态机。

### P0-6 缓存不足的状态被覆盖成“当前未开播”

**代码**

- `pipeline.py:540-543`：容量不足时设置 `error / 缓存空间不足` 并返回 False。
- `pipeline.py:513-517`：外层 target loop 在 `record_and_upload()` 返回 False 后无条件设置 `offline / 当前未开播`，把错误信息覆盖掉。

**影响**

- 用户看到“未开播”，但真实原因是“空间不足”；这也解释了为什么“新主播不能正常录制”看起来像检测问题。

### P0-7 烧录失败会静默降级上传未烧录视频

**代码**

- `pipeline.py:1035-1050`：`record_danmaku=True` 时先尝试 `_prepare_danmaku_part()`；如果渲染失败返回 None，代码**继续执行** `media.process_file()`，把原始 FLV/转码文件当作最终视频上传。

**影响**

- 渲染失败（例如关机中断、字体/编码错误）时，B站/网盘收到的是**没有弹幕**的视频，且状态仍可能显示“上传成功”。
- 这违反“爆弹幕需要烧录进视频”和“只上传烧录后的最终视频”。
- 历史云盘错误里出现 `.flv` 上传，也与该降级路径一致。

## P1：云端与稳定性

### P1-1 当前架构无法使用夸克 VIP“快速通道”

**证据**

- `~/.config/rclone/rclone.conf`：`[quark] type=webdav url=http://127.0.0.1:5244/dav`。
- `openlist_api.py`：实际走 OpenList `/api/fs/put`，单连接、非分片。
- 审阅当时 `quarkpan`、`kuake-pipe`、`bypy`、`quarkclouddrive` 均未安装。2026-10-20 v2.4.0 复核时夸克官方客户端已安装为 `7.4.0.818`，但 `backup.db` 中电脑备份任务数为 0。
- v2.4.0 已使用官方客户端电脑备份目录，并增加客户端/任务/远端三项诊断；不会再以 OpenList 冒充快速通道。
- v2.3.0 新增的 `QuarkCliDriver` 只是调用外部 CLI；CLI 不存在时会回退 OpenList（`cloud/quark.py:124-129`）。

**结论**

- 夸克 VIP 加速只作用于官方客户端通道，不会加速 OpenList/WebDAV/第三方 API。
- 当前代码里不存在真正的“快速通道”；只改驱动名或加 `--concurrency` 不会改变链路。
- 若要快速通道，只有两条现实路线：
  1. 官方客户端 + 监听上传目录（走官方通道，但需要 macOS 自动化/客户端常驻）。
  2. 真正的夸克私有 API 分片并发实现（不是 VIP 通道，且要接受风控风险）。

### P1-2 OpenList token 过期不会自动刷新

**代码**

- `openlist_api.py:129-148`：只有 HTTP `401` 才重新登录。
- 实机错误说明请求没有进入 HTTP 401 的重登分支；OpenList 在这种情况下通常以 HTTP 200 + JSON `code: 401 / message: "token is expired"` 返回，当前逻辑会直接抛错。
- token 缓存在 `_token`，进程不重启就一直是过期 token。

**实机证据**

- 会话记录中 7 次：
  `OpenList 原生上传失败：token is expired`

**影响**

- 云盘上传会持续失败，直到重启整个应用；用户感知为“云盘一直有问题”。

### P1-3 云盘任务与本地清理存在竞态，且“事后开启网盘”不可恢复

**实机证据**

- 多条会话：`cloud_status=FAILED` 且 `path=''`、`source_path=''`。
- 错误包括：`P01 has no local files to back up`。

**代码**

- `pipeline.py:1269+`：入队时检查文件存在，但真正上传在另一个线程池；期间 `cleanup_completed_parts()` 可能已经删除文件。
- 对历史上已经删除本地文件的分段，再开启“网盘备份”会生成不可完成的云端任务（文件已不存在）。

**影响**

- 网盘任务永远 FAILED，且无法补传；UI 上表现为“云盘坏了”。

### P1-4 v2.3.0 的“带宽调度”让云盘更慢

**代码**

- `bandwidth.py:82-92`：只要有 B站上传在进行，且未配置限速，云盘上传自动被压到 **2048 kbps**。
- `bandwidth.py:65-80` + `pipeline.py:1316`：云盘上传全局串行（默认 `max_concurrency=1`）。

**影响**

- 与需求“网盘上传与 B站上传相互独立、并行执行”冲突。
- B站上传频繁时，云盘会长期只有 2 Mbps，用户会直接感觉“网盘不走”。
- 这是 v2.3.0 的新回归（实机 v2.2.68 尚未包含），上线前必须修正默认值或策略。

### P1-5 云盘上传没有断点续传

**代码**

- OpenList 原生 `PUT /api/fs/put` 一次性上传整个文件，失败后只能整文件重传。
- rclone 回退 `copyto` 也是单文件单流。

**影响**

- 9 GB 文件在 14.5 Mbps 下约 1.5 小时；任何一次断线都会从头开始。
- 这是“云盘不稳定/慢”的结构性原因，不是重试次数能解决的。

### P1-6 删除/暂停主播不会立即终止正在下载的 biliup 进程

**代码**

- `pipeline.py:557-643`：内层循环因 `_removed_targets` 或暂停而 break 后，没有 `process.terminate()`；随后继续收尾、等待上传。
- `recorder.py` 的子进程只有在全局 `request_pause()` 或应用退出时才会被统一终止。

**影响**

- 删除主播后，biliup 可能继续下载/写文件一段时间；与“删除主播后相关线程和任务必须停止”不符。

### P1-7 B站长标题的 append 幂等性有风险

**代码**

- `uploader.py`：`find_bvid_by_title` / `_wait_for_bvid` 依赖 `biliup list` 返回的标题精确匹配。
- B站标题有长度上限，过长的“主播名 + 时间 + 房间标题 + Pxx”可能被截断，导致核对失败 → 超时 → 重试时可能重复投稿。

**影响**

- 长房间标题主播可能重复建稿或长时间处于“待核验”。

## P2：画质与体验

### P2-1 弹幕烧录画质

**代码**

- `danmaku.py:14`：原画上限固定 `24000 kbps`（1080p 16 Mbps、720p 8 Mbps）。
- `danmaku.py:185-213`：优先 `h264_videotoolbox` 固定码率；失败后 `libx264 -preset veryfast` 固定码率；没有 CRF。
- `danmaku.py:240`：`probe_video_bitrate()` 已实现，但**从未使用**。
- `quality=origin` 且源为 2K/4K 时仍被压到 24 Mbps 上限。

**实机样本**

- `imxiaoxin P01`：源 FLV 1080p60、18.4 Mbps、3672 秒；输出 MP4 1080p60、20.1 Mbps、3601 秒。
- 输出码率并不低于源，说明这次“糊”更可能是：
  1. VideoToolbox 二次编码的纹理损失；
  2. B站转码后的播放清晰度；
  3. 输出时长比源短 70 秒（时间戳/丢帧），需要单独核对。

**建议**

- 本地与 B站“原画 1080P60”对比后再判定是本地编码还是B站转码。
- 若本地糊：改用 `libx264 -crf 18~20 -preset medium`（或 VideoToolbox 的 quality 模式），以源码率作为下限，保留分辨率/帧率。
- 若 B站糊：这是B站转码策略，需调整投稿参数或提醒用户选“原画”。

**v2.3.1 修复**：默认改为 `libx264 CRF18/20 -preset medium`，`-movflags +faststart`；速度模式以源码率为下限。实机 120 秒素材渲染 1080p60 / 18.7 Mbps，抽帧清晰。

### P2-2 新主播默认排班是硬编码的周一时段

- `web/app.js:1172`、`:1698`：每个新主播都被塞入 `[1,3,5] 20:00-23:00` 的排班，即使当前是 manual/all_day。
- 用户以后切到 scheduled 会继承一个并不属于该主播的时段，容易误判“排班保存后跳回/不生效”。

**v2.3.1 修复**：新主播默认 `all_day`，排班默认为空；`test_new_targets_default_to_all_day_without_schedule` 覆盖。

### P2-3 保存提示误导

- **更正**：主循环会热更新目标配置，只有“当前分段”仍使用旧参数；原提示文案过于模糊。
- **v2.3.1 修复**：保存提示改为“设置已保存；当前分段继续使用旧参数，下一段将应用新设置”。

### P2-4 测试与部署

- 仓库：`171 passed, 1 failed`（唯一失败是沙箱禁止 socket bind，非代码缺陷）。
- 审阅当时实机仍为 v2.2.68；该结论是历史快照。v2.3.1 和 v2.4.0 已重新打包，当前交付看 `dist/DouyinBiliRecorder.app`。
- 在重新打包并重启前，用户看到的所有问题都来自 v2.2.68 行为。

## 建议修复顺序（待确认后执行）

1. **P0 录制可用性**：空间策略（去掉 18 GB 硬预留/按实际剩余容量降级）、目标配置热重启、暂停/删除真正生效、URL 规范化、烧录失败不回退上传。
2. **P0 云端可信性**：token JSON 401 自动重登、任务与清理加锁、禁止给无本地文件的历史分段建云任务、删除规则加数据库不变量。
3. **云端路线决策**：官方客户端目录监听 vs 真正私有 API 分片；在此之前不要宣传“快速通道”。
4. **P1 稳定性**：目标删除终止子进程；长标题截断后的幂等校验。
5. **P2 画质**：CRF/质量模式 + 源码率下限；本地 MP4 与B站原画对比后再定最终参数。
6. **部署**：构建 v2.3.x、升级本地 App、用真实数据回归；否则所有修复都不会作用到实机。
